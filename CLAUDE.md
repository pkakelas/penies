# bouzouki / Πενιές (Penies)

Penies is a site for practising bouzouki over real recordings. A song from YouTube is split into stems with MVSEP; the site plays the backing with the lead bouzouki and the vocals on switches, at 50–150% speed without changing pitch. The site is in Greek (default, at `/`) and English (`/en`).

How a song gets onto the site:

1. An admin signs in at `/admin` and pastes a YouTube link. The page inserts a `songs` row with status `queued`.
2. `worker.py`, running on the user's Mac, picks the row up, runs the split, uploads three stems to Supabase Storage and sets the row to `draft`.
3. The admin opens the draft's song page (only admins can see it), fixes title and artist, and presses Publish. Published songs are listed on the landing page.

Songs are only processed while the worker is running. Supabase cannot run `yt-dlp` or wait on MVSEP, which is why the worker lives on the Mac.

## Layout

- `guitar_split.py`: the MVSEP pipeline, usable as a CLI and imported by the worker (`split_song(url, folder, report=...)`). It downloads the audio with `yt-dlp` and starts one run of the MVSEP preset `mpouzouki` (`PRESET_ID = 2644`), which returns three stems:
  - `lead-guitar`: the "lead guitar" of MVSEP's "Lead/Rhythm Guitar" model (two-stage). This is the bouzouki in these songs.
  - `vocals`: BS PolarFormer (124 bands) run on the Lead/Rhythm model's "no guitar" output.
  - `instruments`: that vocal model's instrumental plus the rhythm guitar, added together by a Mix node.
  - The preset is a graph edited at https://mvsep.com/presets and is private to the user's MVSEP account. The names above are the labels of its Output nodes (all MP3 320 kbps); `guitar_split.py` matches the result files by those labels, so renaming an Output breaks the pipeline. To change models, edit the preset there; the code does not choose them.
- `worker.py`: the link between Supabase and the pipeline. Commands:
  - `uv run worker.py`: watch for queued songs and process them (resumes a song left in `processing`).
  - `uv run worker.py once`: process what is waiting, then exit.
  - `uv run worker.py add-admin USERNAME`: create an `/admin` login, or reset its password. Asks for the password in the terminal.
  - `uv run worker.py import FOLDER --url URL [--title T --artist A --publish]`: upload a song folder that was already split locally.
  - Intermediate files go to `work/<song id>/`; the folder is deleted on success and kept on failure so a retry does not pay for the MVSEP jobs again.
- `supabase/`: `config.toml` and the migration that defines everything in the database (`migrations/20261106150000_songs.sql`).
- `web/`: the Next.js site (see below).
- `stems/player.html` + `stems/SignalsmithStretch.js`: the earlier standalone player, which opens a local song folder straight from disk. `stems/<song>/` holds local copies of a song's stems (five files in folders made before the preset, three now; it plays both). Not used by the site.
- `.claude/launch.json`: starts the site's dev server for the preview pane.

## Supabase

- Organisation `bouzouki`, project `penia` (ref `vmcjcicqcacwlnfozyyi`, eu-central-1). There is no Docker on this Mac, so there is no local Supabase: everything runs against this cloud project.
- `songs`: `status` is `queued → processing → draft → published` (or `failed`, with `error`; a draft that did not split well can be `archived`, which keeps its stems, is admin-only like a draft and is listed on `/admin/archive`, from where it goes back to the drafts); `step`/`step_detail` show the worker's progress; `stems` maps stem name → path in the bucket; `slug` is the page address: the database makes it from the title whenever the title is set or changes (`slugify()` transliterates Greek, `-2`, `-3`… on a clash; trigger `songs_slug_follows_title`), and the video id stands in until there is a title. The addresses a song had before are kept in `old_slugs`, and the song page redirects them to the current one; `artist` is who sings in this recording, `first_performed` (free text, often only a year) and `first_singer` are the song's first performance, `composer` wrote the music, `requested_by` is the visitor who asked for the song (the name from the request form; empty when nobody asked). Admins fill these in; the song page and the landing page's list show them. `instrumental` (ticked in `/admin` when adding the link, or on the card later) marks a song with no singer: the worker leaves out the `vocals` stem, the player ignores one if it exists and shows the vocals switch off, and the list says "first played by" instead of "first sung by" (`import --instrumental` does the same). `start_seconds`/`end_seconds` (null = the recording's own start/end) cut an intro or outro: the admin types them as m:ss, the player keeps only that part (position 0:00 is the start, `playableLength()` in `web/src/lib/supabase.ts` is what the list shows).
  `sort_order` is the place in the landing page's list (null = not placed yet, shown first, newest first): the arrows in `/admin` call `reorder_songs(ids)`, which numbers every published song from 1; `orderSongs()` in `web/src/lib/supabase.ts` and the query in `web/src/lib/songs.ts` must sort the same way.
- `song_requests`: the songs visitors asked for (`song` as typed, the visitor's `name` and `email`, `lang` of the page). A signed-in visitor asks for one song at a time from the request dialog, which takes one of their credits (see Credits) and saves the row already paid (`paid_at`, shown as "Paid" in `/admin`). Split only paid requests. Until 10 Nov 2026 the form saved three songs before the payment (they share `form`, an id the browser made up; `seq` is the order they were typed in), so older rows may be unpaid, and those from before 9 Nov have no mark at all (check them in Stripe); requests from before 9 Nov have no `name`. Visitors may still insert unpaid rows directly (only `song`, `name`, `email`, `lang`, `form`), which a page left open since before credits does; a trigger refuses new rows once 30 arrived within an hour. Admins read and delete them in `/admin`. The dialog promises the song within 24 hours. Each song asked for emails an alert to pkakelas@gmail.com saying whether it is paid (trigger `song_requests_alert`, which runs once per insert and writes one mail per email address in it: pg_net posts to Resend's API with the Vault secret `resend_api_key`; with no such secret nothing is sent, and a failed mail never loses the requests). Reply to the alert to answer the visitor.
- Payments: Stripe's webhook posts to the database function `stripe_webhook` (`https://<project>.supabase.co/rest/v1/rpc/stripe_webhook?apikey=<publishable key>`, events `checkout.session.completed` and `checkout.session.async_payment_succeeded`). It checks Stripe's signature against the Vault secrets whose names start with `stripe_webhook_secret` (with none, every call is refused), records the payment once in `song_payments` (by Checkout Session id, so a payment seen twice counts once), adds a pack of credits (`song_pack_paid(checkout)`, migration `20261110180000_song_pack_from_link.sql`, tells the pack first from the `songs` metadata that each Payment Link carries (1, 3 or 5; Stripe copies a link's metadata to its payments), and failing that from the amount in euros, the payment's `amount_subtotal`, or `currency_conversion.amount_subtotal` when Adaptive Pricing charged another currency, through `song_pack(cents)`: 1 song for 3 €, 3 for 6 €, 5 for 10 €, and any other amount buys `song_pack()`, 3) to `song_credits` under the email of the visitor whose user id is the payment's `client_reference_id` (whatever email they paid with), and mails them a confirmation saying how many songs they have (`song_request_receipt(lang, songs, left_over)` builds it, Greek or English; its texts are in that function, last defined in the migration `20261110160000_song_credits.sql`, not in `i18n.ts`; keep them in step with the dialog's). A payment from a page open since before credits has a request form's id as its reference, or none: then the form's requests (with no reference, the last unpaid form of the payer's email) are marked paid and use up that much of the pack, and whatever is left goes under the form's email. The mail goes through Resend from `paraggelies@penies.gr`, which Resend only accepts once penies.gr is a verified domain there; replies go to pkakelas@gmail.com. `net._http_response` keeps Resend's answers for a few hours.
- Credits: `song_credits` (email → `balance`) holds songs paid for and not asked for yet. A visitor signs in with their email (Supabase Auth email code, see below), buys a pack and spends it from the request dialog: `my_song_credits()` gives the balance, `my_song_requests()` the songs they are waiting for (paid requests not yet deleted with Done) and `spend_song_credits(songs, name, lang)` takes one credit per song and saves them as paid requests, all going by `visitor_email()` (the signed-in user's email, only once confirmed). Visitors cannot read the tables. To give someone credits by hand, add to their row in `song_credits` (email in lower case).
- `admins` + `is_admin()`: who may use `/admin`. Row-level security: anyone reads published songs; admins read and change everything. A song cannot be published without stems.
- Bucket `stems` (private): `<song id>/<stem>.mp3` for `instruments`, `lead-guitar`, `vocals`. Songs split before the preset also have `rhythm-guitar`, which is not inside their `instruments`; the player adds it to the backing when a song has it. A stem can be downloaded by whoever can read its song, so a draft's audio is admin-only. About 24 MB per song.
- Visitors may sign in, only with a code sent to their email, so that they can spend credits; signing in gives them nothing else (every rule asks `is_admin()`). The code mail is `supabase/templates/sign-in-code.html`, used as both the "Confirm signup" and the "Magic link" template (a new address gets the first); it goes out through Resend's SMTP from `paraggelies@penies.gr` (Supabase's own mailer only writes to the organisation's members and, on the free plan, allows no other template). These settings, sign-ups being on and the 6-digit code are in the `[auth]` sections of `supabase/config.toml` and reach the project with `supabase config push --project-ref vmcjcicqcacwlnfozyyi`: it shows what differs and asks per section; answer yes to auth only, and only with Resend's key in `RESEND_API_KEY` (it is the SMTP password; without it the push would save the literal text `env(RESEND_API_KEY)`). The storage section's differences are the file's local defaults, not something to push. An admin "username" is the Supabase Auth email `username@admin.penia.app` (`ADMIN_EMAIL_DOMAIN`, defined in both `worker.py` and `web/src/lib/supabase.ts`; keep them equal).
- Schema changes: add a migration, then `supabase db push` (needs `SUPABASE_DB_PASSWORD` from `.env`). Push a migration before deploying site code that reads what it adds.
- There is no `robots.txt`, on purpose: the admin pages keep themselves out of search results with a noindex tag (`robots` in their `metadata`), and a crawler only sees that tag if it is allowed to fetch the page.

## Secrets

- `.env` (git-ignored): `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_PASSWORD`, `MVSEP_API_TOKEN`. Used by `worker.py` and `guitar_split.py`. Never print, commit or share these. `.env.example` lists the names.
- `.env.admin` (git-ignored): the username and generated password of the `/admin` login `pkakelas`. Never print or share it. It goes stale if the password is changed with `add-admin`.
- Vault secret `resend_api_key` (in the database, not in a file): Resend's API key (sending only), used by the request alert and the payment confirmation. The same key is the SMTP password of the project's sign-in mails (see Supabase), so a new key has to be pushed there too. Add or change it with `select vault.create_secret('re_…', 'resend_api_key')` / `vault.update_secret(...)`.
- Vault secret `stripe_webhook_secret`: the signing secret (`whsec_…`) of the Stripe webhook endpoint. The sandbox's endpoint has its own; save it under another name with the same start, such as `stripe_webhook_secret_sandbox`.
- `web/.env.local` (git-ignored): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `NEXT_PUBLIC_PAYMENT_LINK_1`, `_3`, `_5` (the payment link of each pack). These are meant for the browser; the secret key must never go into `web/`.

## The site (`web/`)

Next.js 16 (App Router, React 19, Tailwind v4) with `cacheComponents`. **This Next.js differs from older versions: read the relevant guide in `web/node_modules/next/dist/docs/` before changing routing, caching or data loading** (see `web/AGENTS.md`).

- Routes: `src/app/(el)/…` is the Greek site and `src/app/(en)/en/…` the English one, each with its own root layout (so `<html lang>` is right). Pages: landing, `songs/[slug]`, `orders`, `admin`, `admin/archive`. The route files are one-liners; the pages themselves are in `src/components/` and take a `lang` prop.
- `src/lib/i18n.ts`: every piece of text in both languages. New text goes here, in both.
- `src/lib/songs.ts`: published songs for server rendering, cached (`"use cache"`, tag `songs`). `/admin` calls `refreshSongs()` (`src/app/actions.ts`) after a change so public pages update at once.
- `src/components/SongRoute.tsx`: a song page. An old address of a renamed song redirects to its current one. If no published song has the slug, `DraftPreview` asks again from the browser with the admin's sign-in, which is how drafts are tested.
- `src/lib/engine.ts` + `src/components/Player.tsx`: the player. The stems are mixed into six channels (0-1 backing = instruments, plus rhythm guitar in songs that have it as a separate stem, 2-3 vocals, 4-5 lead) and fed to one Signalsmith Stretch node (`public/vendor/SignalsmithStretch.js`, npm `signalsmith-stretch` 1.3.2, MIT, unmodified, loaded as a plain script); one node keeps the stems in sync and does the time-stretch. Position is tracked in the engine (`anchorPos`/`anchorTime`/`rate`) and every play, seek and speed change is sent with `stretch.schedule(...)`. On Android the engine also plays a silent `<audio>` element in a loop while the song plays: Web Audio alone does not count as playing media there, so the system slows a browser in the background and the sound breaks up. Pausing that element (the media notification, a phone call) pauses the song, and the engine tells the player through `onchange`. The notification gets the song's own length and position from `report()` (Media Session; left alone it shows the silent element's ten seconds), its bar seeks, and `Player` gives it the title and artist. Also Android only, to need less of the processor in the background: the stretcher's `cheaper` preset and a 0.1 s output buffer (`latencyHint`), which makes pause and the switches that much later.
- `src/components/SongList.tsx`: the landing page's list. Each song is a 78 rpm record (inline SVG) with the first-performance date on its label; the composer sits under the title and the first and current singers beside the record. The last row is a record with an empty label and a "+", which opens the request form (`SongSearch` puts it in the list; it stays while the list is narrowed). The motion is CSS in `globals.css`: `.disc-spin` on hover, `.disc-roll` on scroll.
- `src/components/SongSearch.tsx` + `src/lib/search.ts`: the search box above the list. `SongList` draws every row on the server and hands them over with a `searchKey()` of the song's text (title, composer, singers, year); typing only hides rows. A key is how the text sounds in Latin letters, so accents, capitals and Greek or Latin spelling make no difference ("Χιώτης" = "xiotis" = "chiotis"). When nothing matches, a second request button opens the form with what was typed. Under the box are two rows of buttons, labelled "Μουσική" and "Ερμηνεία": one button per composer and one per singer (first singers and the ones in the recording together), most songs first; a button shows only that person's songs. The fields are split at commas and two spellings with the same `searchKey()` are one person. Only one thing narrows the list at a time: typing lets go of the person chosen, and choosing a person empties the box and lets go of the one before, so a choice made earlier never makes a search come up empty.
- `src/components/SongRequest.tsx`: the "Request songs" button and its dialog. The button is in the top bar of every page but `/admin` and under the landing page's title, beside a line saying that requests are taken; the list's last row opens the same dialog (given as `children`, the row is the button). A visitor first signs in: their email, then the code mailed to it (an admin's sign-in does not count here). Signed in, the dialog says how many songs they have left, links to the orders page with how many songs they are waiting for (`request.askedOne`/`askedMany`), and has a row marked "+" for the next one (an example song as its placeholder, `request.examples` in `i18n.ts`), with their name under it (kept in the user's metadata after the first song) and Send, which spends one credit. Sending a song turns the dialog into a thank-you (`request.thanks`, `thanksNote`) with that link, a button back to the next song while there are songs left (`request.more`) or to the packs when there are none (`request.buyMore`), and Close. With no songs left the dialog offers the packs (`request.packs` in `i18n.ts`: 1, 3 or 5 songs; a pack's price is written there, set on its Stripe link and listed in the database's `song_pack(cents)`, and the three must agree), says under them what a pack is (`request.perks`: the songs can be asked for at any time and do not expire, ready within 24 hours, the original recording unless there is no good remaster of it) and the button is Pay: it goes to the chosen pack's Stripe Payment Link (`NEXT_PUBLIC_PAYMENT_LINK_1`, `_3` or `_5`, by the number of songs; a pack without a link is not offered), given the visitor's user id as `client_reference_id`, their email and the page's language; with no link at all only the pack of 3 is shown and the button only shows the error text. Every link must be set up in Stripe to send people back to `/?paid`, where the top bar's dialog opens saying the payment was made and looks every two seconds until the new songs are there (an English visitor is passed on to `/en?paid`). The links are in the Stripe account of Albatross Consulting E.E. (customers see its trading name, "Penies.gr", and the site's pick as its icon; both are set in the live account's Business settings). The live ones (on Vercel) send people back to `https://www.penies.gr/?paid` and each has the metadata `songs` (its pack): "Πενιές · 1 τραγούδι" (3 €, `https://buy.stripe.com/dRmdR10Ul5T00xCg3ofMA01`), "Πενιές · 3 τραγούδια" (6 €, `https://buy.stripe.com/bJedR1gTj5T0gwA3gCfMA02`) and "Πενιές · 5 τραγούδια" (10 €, `https://buy.stripe.com/dRmcMX32t2GO5RW18ufMA03`). The older link `penies` (5 € for 3 songs, `https://buy.stripe.com/4gM14fauV95ca8c3gCfMA00`) is for the site from before the packs; deactivate it once they are deployed. The account's test mode has the same three links with the same names, prices and metadata (test cards only), in `web/.env.local`; they send people back to `http://localhost:3001/?paid`, where the preview pane's dev server was running when they were made (if it comes up on another port, change the links' confirmation page in Stripe). Test mode has no webhook to the database, on purpose: there is only the live database, and a test payment must not give real credits. So a test payment goes through on Stripe's side and adds no songs; give test credits by hand (see Credits). The page itself does not know whether a payment really happened (anyone can open `/?paid`); the database does, from Stripe's webhook (see `song_requests`).
- `src/components/Orders.tsx`: `/orders` (`/en/orders`), the songs the signed-in visitor is waiting for (`my_song_requests()`, so a song leaves it when Done is pressed in `/admin`), numbered like a setlist, with the request button under them; signed out, it says to sign in, which is done in that button's dialog. The dialog sends `REQUESTS_CHANGED` on the window when it signs in or out or sends a song, and the page looks again. Kept out of search results like the admin pages.
- `src/components/Admin.tsx`: sign-in, the open song requests with who asked (Done deletes one; the name is typed into the song's "requested by" by hand), add a video, progress of the worker (polled every 4 s while something is queued or processing), edit, test, publish/unpublish, archive a draft, delete. Each song is a card that starts closed, showing only its title. With `archive` it is `/admin/archive`: the archived songs, each with a button back to the drafts.
- `src/components/Header.tsx`: the top bar (with the request button) and the footer. The footer says "Made with ♥" (no name) and gives an email address to write to (`CONTACT`).
- `src/components/Strings.tsx`: the bouzouki strings on the landing page (canvas; they vibrate under the pointer, with no sound).
- Design: warm black, cream and brass (colours and the `.range` slider in `src/app/globals.css`); Noto Serif Display for titles, Commissioner for text, both with Greek.

## Running

```bash
uv run worker.py              # process songs added in /admin (leave it running)
npm --prefix web run dev      # the site at http://localhost:3000
```

- Checks for the site: `npm --prefix web run build` and `npm --prefix web run lint`.
- The pipeline alone, without Supabase: `uv run guitar_split.py "https://www.youtube.com/watch?v=VIDEO_ID"` saves three stems into `stems/<video title>/`. Re-running is safe: a folder that has its stems is skipped and a submitted run is resumed from `.mvsep-jobs.json` in the song folder.
- Python dependencies (`yt-dlp`, `requests`) are declared inline in the scripts and installed by `uv`. There is no `ffmpeg` on this machine and none is needed.
- The site is on Vercel: project `penia` (team `dimitris-lamprinos-projects`, framework preset Next.js, root directory `web`), https://penia-one.vercel.app, connected to the GitHub repository `pkakelas/penia`. A push to `main` deploys to production; other branches get preview deployments. Env vars on Vercel: the two `NEXT_PUBLIC_SUPABASE_*` (Production and Preview) and `NEXT_PUBLIC_PAYMENT_LINK_1`, `_3`, `_5` (Production only: the live links; `NEXT_PUBLIC_PAYMENT_LINK` without a number is the old 5 € link, read by no code since the packs).

## MVSEP API notes

- Docs: https://mvsep.com/full_api
- The account is premium (bought credits). A run of the preset costs 2 credits per minute of audio (1 per model), so about 8 for a four-minute song; `GET /api/app/user?api_token=...` shows the credits left (`premium_minutes`).
- Create: `POST /api/separation/create` with `preset_id` (then `sep_type`, `add_opt*` and `output_format` are ignored); poll: `GET /api/separation/get?hash=...&api_token=...`. A preset run is only visible with the token of the account that started it; without it the answer is `not_found`.
- A finished run has `data.type = "preset_run"` and one entry in `data.files` per Output node; the entry's `type` is that node's label.
- The token is in the URL of the poll request, and `requests` quotes the URL in its exceptions. Never put such an exception's text into the `songs.error` column or the log (`wait_for_result` reports only the kind of error).
- `GET /api/app/algorithms` (no token) lists every model with its `render_id` (= `sep_type`), options and SDR scores. The preset editor offers the same models as nodes, plus Mix (adds its inputs), Gain, Ensemble, Invert and others.
